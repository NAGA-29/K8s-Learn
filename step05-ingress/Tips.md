# Ingress Tips: API v1 / v2 の共存方法

## API バージョンとデプロイ単位は別に考える

Ingress を使うと、API のバージョンごとにリクエスト先を分けられる。

```text
/api/v1 → api-v1-service → api-v1 Deployment → v1 Pod 群
/api/v2 → api-v2-service → api-v2 Deployment → v2 Pod 群
```

この構成では、v1 と v2 を独立してデプロイ、スケール、停止できる。v1 の提供終了時に v2 を変更したり再デプロイしたりする必要もない。

ただし、API のバージョンが異なるからといって、必ず Deployment まで分ける必要があるわけではない。API バージョンはクライアントに公開する契約の違いであり、Deployment はアプリケーションのリリースや運用の単位だからである。

## 主な構成パターン

| 構成 | 適しているケース |
|---|---|
| 1つのアプリが v1 と v2 の両方を処理する | 処理やデータモデルの大部分が共通しており、違いが入出力形式や一部の振る舞いに限られる |
| v1 と v2 を別 Deployment にする | v2 が大幅な再設計、別言語、別データストアで実装される、または負荷特性やリリース周期が異なる |
| 最初は同居させ、段階的に分離する | 既存システムを停止せず、少しずつ新しい実装へ移行する |

大規模な刷新で段階的に旧システムを置き換える方法は、一般に **Strangler Fig パターン** と呼ばれる。

## Ingress で v1 / v2 を分ける例

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: api.k8s-learning.local
      http:
        paths:
          - path: /api/v1
            pathType: Prefix
            backend:
              service:
                name: api-v1-service
                port:
                  number: 8080
          - path: /api/v2
            pathType: Prefix
            backend:
              service:
                name: api-v2-service
                port:
                  number: 8080
```

Ingress は API のバージョンを実行するのではなく、URL のパスを見て適切な Service に転送する。各 Service は、それぞれの Deployment が作成した Pod 群へリクエストを振り分ける。

## v1 と v2 を分離する利点

- バージョンごとに独立してデプロイできる
- バージョンごとに Pod 数やリソース量を変更できる
- v1 の障害や変更が v2 に影響しにくい
- v1 を廃止するとき、経路とリソースを独立して削除できる
- 実装言語やフレームワークをバージョンごとに変更できる

## 分離によって増えるコスト

- Deployment、Service、監視、アラート、CI/CD が二重になる
- セキュリティ修正を両方へ適用する必要がある
- 認証や入力検証などの共通処理が重複しやすい
- ログやメトリクスの調査対象が増える
- データベースを共有する場合、スキーマの後方互換性が引き続き必要になる

分離すると「v1 を捨てる瞬間」は軽くなるが、「v1 と v2 が共存する期間」の運用負荷は大きくなる。

## v1 を廃止するときの流れ

1. アクセスログやメトリクスで v1 の利用状況を確認する
2. 利用者へ廃止予定を通知し、v2 への移行期間を設ける
3. v1 への新規利用を停止する
4. Ingress から `/api/v1` のルートを削除する
5. `api-v1` の Deployment と Service を削除する
6. v1 専用の設定、監視、データ、CI/CD を削除する

Ingress の設定を削除できても、利用中のクライアントが残っていれば API を安全に廃止したことにはならない。実際の廃止作業では、Kubernetes リソースの削除よりも、利用状況の把握とクライアントの移行が重要になる。

## Pod ではなく Deployment 単位で考える

Kubernetes では、v1 コンテナと v2 コンテナを1つの Pod に詰める構成は通常選ばない。Pod 内のコンテナは同時に起動・停止・スケールするため、バージョンを独立して管理できなくなるからである。

同居させる場合は、1つのアプリケーションプロセスが v1 と v2 の両方の Router を持つ。分離する場合は、v1 と v2 をそれぞれ別の Deployment と Service にする。

## 判断の目安

> API 契約だけが違うなら同居させ、実装・データ・リリース・スケーリングのライフサイクルまで異なるなら分離する。

分離するか迷う場合は、次の項目を確認する。

- v1 と v2 を別々のタイミングでリリースしたいか
- 必要な Pod 数やリソース量が異なるか
- 障害の影響範囲を分離する必要があるか
- 実装やデータモデルの共通部分がどれくらい残っているか
- v1 と v2 が共存する期間はどれくらいか
- 二重化する運用コストを負担できるか

バージョン番号だけを理由にサービスを分けるのではなく、独立した運用ライフサイクルが必要かどうかを基準に判断する。
