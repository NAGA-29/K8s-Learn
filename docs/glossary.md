# Kubernetes 用語集

Kubernetes初心者向けの用語集です。各用語に実用的な説明と、なぜ重要かを添えています。

---

### Node

Kubernetesクラスタを構成する個々のマシン（物理または仮想）。Podはすべていずれかのノード上で実行される。Control Plane用のマスターノードとワークロードを動かすワーカーノードがある。

**なぜ重要か:** クラスタのリソース（CPU・メモリ）はノードの合計で決まるため、スケーリングやリソース管理の基本単位となる。

### Pod

Kubernetesにおけるデプロイの最小単位。1つ以上のコンテナをまとめたグループで、同一Pod内のコンテナはネットワークとストレージを共有する。通常は1 Pod = 1コンテナで運用することが多い。

**なぜ重要か:** すべてのワークロードはPodとして動作するため、Kubernetesを理解する上で最も基本的な概念である。

### Deployment

Podのデプロイとアップデートを宣言的に管理するリソース。ローリングアップデートやロールバックを自動で行える。内部的にはReplicaSetを作成・管理する。

**なぜ重要か:** 本番環境でPodを直接作ることはほぼなく、Deploymentを通じて管理するのが標準的なやり方である。

### ReplicaSet

指定した数のPodレプリカが常に稼働していることを保証するリソース。Podが落ちると自動的に新しいPodを起動して数を維持する。通常はDeploymentが自動的に管理するため、直接操作することは少ない。

**なぜ重要か:** 可用性を保つ仕組みの中核であり、Deploymentのローリングアップデートの裏側で新旧のReplicaSetが切り替わる。

### Service

Podの集合に対して安定したネットワークエンドポイント（IPアドレスとDNS名）を提供するリソース。Pod自体はIPアドレスが変わるが、Serviceを通じてアクセスすることで常に到達できる。ClusterIP、NodePort、LoadBalancerなどのタイプがある。

**なぜ重要か:** Podは頻繁に再起動・スケールするためIPが変わるが、Serviceがあれば安定した通信経路を確保できる。

### Ingress

クラスタ外部からのHTTP/HTTPSトラフィックをクラスタ内のServiceにルーティングするリソース。ホスト名やパスベースのルーティング、TLS終端が可能。動作にはIngress Controller（nginx-ingress等）が必要。

**なぜ重要か:** 本番環境で外部公開するWebアプリケーションには必須であり、1つのロードバランサで複数サービスを公開できる。

### ConfigMap

設定値（環境変数、設定ファイルなど）をPodの外部で管理するためのリソース。アプリケーションの設定をコンテナイメージから分離することで、同じイメージを異なる環境で使い回せる。

**なぜ重要か:** 設定変更のたびにイメージを再ビルドする必要がなくなり、環境ごとの設定管理が容易になる。

### Secret

パスワード、トークン、証明書などの機密情報を格納するリソース。ConfigMapと似ているが、Base64エンコードされて保存され、アクセス制御をより厳密に行える。ただしデフォルトではetcd上で暗号化されていない点に注意。

**なぜ重要か:** 機密情報をマニフェストやコンテナイメージにハードコードするのは危険であり、Secretで安全に管理するのが必須である。

### PVC (PersistentVolumeClaim)

永続ストレージを要求するためのリソース。PVCを作成すると、StorageClassに応じてPersistentVolume（PV）が動的に確保される。Podが削除されてもデータは残る。

**なぜ重要か:** データベースやファイルストレージなど、Pod再起動後もデータを保持したいワークロードに不可欠である。

### HPA (Horizontal Pod Autoscaler)

CPU使用率やカスタムメトリクスに基づいてPodの数を自動的に増減するリソース。metrics-serverまたはPrometheusアダプタが必要。最小・最大レプリカ数とターゲット使用率を設定する。

**なぜ重要か:** トラフィックの変動に応じて自動スケールすることで、コスト最適化と可用性の両立を実現できる。

### Probe (liveness / readiness / startup)

Podの状態を定期的にチェックする仕組み。**liveness probe** はコンテナの生存確認（失敗すると再起動）、**readiness probe** はリクエスト受付可否の確認（失敗するとServiceから除外）、**startup probe** は起動完了の確認（起動が遅いアプリ向け）を行う。

**なぜ重要か:** Probeを適切に設定しないと、異常なPodにトラフィックが流れたり、正常なPodが不必要に再起動されたりする。

### Namespace

クラスタ内のリソースを論理的に分割する仕組み。チーム別・環境別にリソースを隔離でき、リソースクォータやRBACと組み合わせてアクセス制御を行える。

**なぜ重要か:** 複数チームや複数環境で1つのクラスタを安全に共有するための基本的な分離単位である。

### WebSocket

HTTPをベースとした双方向通信プロトコル。最初にHTTPでハンドシェイクした後、TCPコネクションを維持してサーバーとクライアントが自由にメッセージを送り合える。チャットやリアルタイム通知で使われる。

**なぜ重要か:** Kubernetesでは長時間接続の維持、Podスケーリング時のコネクション管理、Ingressの設定など、HTTPとは異なる考慮が必要になる。

### Pub/Sub

パブリッシュ・サブスクライブ型のメッセージングパターン。送信者（Publisher）がメッセージをチャネルに発行し、受信者（Subscriber）がチャネルを購読して受け取る。Redis Pub/SubやKafkaなどで実装される。

**なぜ重要か:** WebSocketサーバーが複数Podにスケールした際、Pod間でメッセージを共有するために必須のパターンである。

### StatefulSet

ステートフルなアプリケーション（データベース等）を管理するためのリソース。各Podに安定したネットワーク識別子と永続ストレージが割り当てられ、順序付きのデプロイ・スケーリングが保証される。

**なぜ重要か:** MySQLやRedisのようにデータの永続化やPodの一意性が必要なワークロードでは、Deploymentではなく StatefulSetを使う必要がある。

### DaemonSet

クラスタ内のすべてのノード（または指定ノード）に1つずつPodを配置するリソース。ノードが追加されると自動的にPodが配置され、削除されると除去される。

**なぜ重要か:** ログ収集エージェントやモニタリングエージェントなど、全ノードで動作させたいワークロードに使われる。

### CronJob

cronのスケジュール形式で定期的にJobを実行するリソース。バッチ処理、バックアップ、レポート生成など、定期実行タスクに使う。実行履歴の保持数も設定可能。

**なぜ重要か:** 定期的なメンテナンスタスクやバッチ処理をKubernetesネイティブに管理できる。

### RBAC (Role-Based Access Control)

ロールに基づいてKubernetesリソースへのアクセスを制御する仕組み。Role/ClusterRoleで権限を定義し、RoleBinding/ClusterRoleBindingでユーザーやサービスアカウントに紐づける。

**なぜ重要か:** 本番環境では誰が何を操作できるかを厳密に制御することがセキュリティの基本であり、RBACはその中核を担う。

### CNI (Container Network Interface)

Kubernetesのネットワーク機能を提供するプラグインの仕様。Calico、Flannel、Ciliumなど様々な実装がある。Pod間通信、ネットワークポリシーの適用などを担当する。

**なぜ重要か:** クラスタのネットワーク構成はCNIプラグインの選択によって大きく変わり、パフォーマンスやセキュリティポリシーに直結する。

### CSI (Container Storage Interface)

Kubernetesのストレージ機能を提供するプラグインの仕様。AWS EBS、GCE PD、NFS、Cephなど様々なストレージバックエンドを統一的なインターフェースで利用できる。

**なぜ重要か:** 永続ストレージの選択と構成はステートフルワークロードの信頼性に直結し、CSIによって環境に応じたストレージを柔軟に利用できる。
